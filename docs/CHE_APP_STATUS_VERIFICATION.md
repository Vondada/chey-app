# Current app and backend status

Root cause: informational runtime questions lacked a deterministic route. Most went to the model, while installed build number could be misclassified as an owner preference. The execution guard then refused fabricated repository claims; that guard was correctly rejecting unsupported evidence, but it could not perform the missing lookup. Baseline replay also exposed an unsupported installed-version sentence surviving the model path. Baseline transcripts are retained in docs/verification/app-status-baseline-*.json.

The existing self_update.js and Worker dispatcher now answer these reads before browsing, personal memory or model execution. The runtime source is CF_VERSION_METADATA for the Worker serving this request. A short commit tag is labelled as a tag; full SHA is returned only if supplied or resolved by the existing matching GitHub deployment lookup. Workflow lookup failure does not hide available runtime values. Running metadata alone never establishes that CHE performed a deployment.

Flutter reuses CheInstalledBuild.read and the existing native appVersion channel. Only explicit status requests attach a fresh device-reported bundle version/build. Absent/stale/malformed metadata remains unavailable; the latest release is never treated as the installed copy. Native bundle version does not identify a Shorebird patch. Offline models cannot answer these questions. The explicit Settings/version command opens the existing CHE app/update details page, with visible feedback, haptic feedback and requested speech; it does not claim to open iOS Settings remotely.

Validation: app_status.test.mjs tests trusted metadata, partial hashes, matching lookup, missing/malformed/stale device data, read-only routing and fabricated receipts. memory_truth.test.mjs exercises the six owner prompts through /api/chat with an intentionally dishonest model. Flutter che_app_status_test.dart covers native channel reads, failure without fallback, intent classification and settings routing predicate. CI must run full Worker and Flutter checks before merge. The iPhone still needs physical verification of the installed build, requested speech, Settings details and patch state.

## Device install receipt (2026-10-23)

`POST /api/device/installed` (paired owner device only) takes `{ "version", "build", "patch" }` as the phone reports them (`CheInstalledBuild.read()` and `readPatch()` in `lib/self_update/che_mobile_update.dart`). The Worker writes one `device_install` receipt per distinct build (`device_install:<version>-<build>-<patch|none>`, `confirmed: true`). That receipt is the only evidence the hallucination auditor accepts for "the update is installed on your iPhone"; with no receipt the claim is removed. The Flutter call that posts this report after each successful launch is a follow-up: the endpoint exists and is tested; the app does not call it yet, so no install is claimed as confirmed.
